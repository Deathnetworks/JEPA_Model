# Automated Reinforcement Learning & GRPO Training

This document details concepts and practices for fully automating Group Relative Policy Optimization (GRPO) and Reinforcement Learning (RL) training loops in the Mamba-JEPA ecosystem. The focus is on establishing continuous, hands-free optimization using real code compilers, verifiable programmatic metrics, and dynamic penalty algorithms to generate high-quality data and adapt the model without human intervention.

## 1. Verifiable Code Evaluation

Automating RL for code generation requires deterministic reward signals that replace human subjective grading. We achieve this by embedding a compiler directly into the evaluation loop.

### Sandbox Execution and Compilation
- **Process Isolation**: Generated code (e.g., Rust, Python) must be securely extracted and written to temporary scripts within a sandboxed environment to prevent host system damage.
- **Subprocess Compilation**: Tools like `rustc` are executed via non-blocking subprocesses with strict timeouts (e.g., `timeout=5` seconds) to evaluate syntax, type safety, and architectural validity.
- **Binary Reward Signals**:
  - **Success ($r_{compile} = 1.0$)**: The compiler exits with a `0` code (no errors).
  - **Failure ($r_{compile} = 0.0$)**: The compiler throws an error, or the execution times out.

### Code Extraction Best Practices
- Use robust Regex parsing that leverages hexadecimal escape sequences (e.g., `\x60\x60\x60`) or `chr(96)` for markdown backticks to prevent documentation generators and markdown parsers from truncating or corrupting the text blocks.
- If explicit block markers are missing, fallback heuristics can extract the raw text output for compilation attempts.

## 2. Group Relative Policy Optimization (GRPO)

Traditional PPO relies on separate value networks, which consume excessive memory and computational overhead. GRPO streamlines this by computing relative advantages across a group of simultaneous rollouts.

### The GRPO Loop
1. **Group Rollout Sampling**: For a given prompt, the `MambaJEPAEngine` samples a group of $G$ (e.g., $G=4$) independent trajectories.
2. **Reward Accumulation**: Each generated string is passed through the automated verifier to calculate its absolute reward $r_i$.
3. **Relative Advantage Formulation**: The advantage $A_i$ is calculated by normalizing the group's rewards:
   $$A_i = \frac{r_i - \mu}{\sigma}$$
   where $\mu$ is the mean and $\sigma$ is the standard deviation of the group.
4. **Policy Clipping**: We utilize PPO-style policy clipping (`clip_eps = 0.2`) when updating weights to prevent drastic changes that destabilize the latent representations.

### Continuous Action Spaces (DAPPO)
Because the `MambaGraphRouter` allocates loops continuously, we treat the number of active graph loops as a secondary RL action space:
- **Router Policy Optimization**: The continuous steps taken during generation are tracked and optimized against the relative advantage. The continuous routing ratio uses PPO bounds similar to the token generation policy.
- **Compute Budget Penalty**: To prevent the model from "overthinking" (unnecessary loop accumulation), a penalty proportional to the number of steps is subtracted from the final reward:
  $$r_{final} = r_{compile} - (\gamma \times \text{avg\_loops})$$

## 3. Test-Time Adaptation (AdaJEPA)

RL loops can be executed online during active inference (test-time optimization), transforming catastrophic generation failures into learning opportunities.

### Autonomous Error Correction Loop
1. **Compilation Failure**: If the initial generated code fails the compiler check, the error stream (`stderr`) is captured.
2. **Online GRPO Surrogate Step**: A fast GRPO surrogate loss (e.g., group size $G=2$) is computed.
3. **Penalty Backpropagation**: Gradients are actively backpropagated through the optimizer (e.g., AdamW8bit) to heavily penalize the exact trajectory and routing sequence that led to the compiler error.
4. **Iterative Refinement**: The compiler error string is appended to the original prompt, and the code is regenerated with the newly penalized model state.

## 4. Programmatic Data Quality Metrics

Beyond binary compilation success, automated pipelines can incorporate the following metrics into their reward formulations:

- **Foresight Calibration**: We enforce a Mean Squared Error (MSE) loss between the model's predicted probability of success (generated by the `foresight_head` off the `student_concept`) and the actual verifiable compiler reward.
- **Token Efficiency / Length Penalty**: Shorter, concise code that successfully compiles can be favored over needlessly verbose code.
- **Linter Warnings**: Linters (e.g., `clippy` for Rust) can be used to generate fractional negative rewards for suboptimal code structures or anti-patterns, even if the code technically compiles.
- **Test-Suite Passage**: By generating accompanying unit tests, the reward signal can scale linearly based on the percentage of passing tests.

## 5. Architectural Considerations for Continuous Training

- **Memory Management**: Offload optimizer states to the CPU (via ZeRO-3 or similar mechanisms), but heavily utilize manual VRAM clearing (`torch.xpu.empty_cache()`) during the intermediate steps of chunked GRPO loops.
- **Dynamic Inference Budgeting**: Automatically cap the maximum number of recurrent loops based on sequence complexity (e.g., 1 loop per 64 tokens, capped at 64) to bound execution time during RL sweeps.
- **Mixed Precision Safety**: Ensure operations across the GRPO update and generation loops are wrapped in appropriate mixed precision contexts (`torch.autocast`) to prevent silent nan-gradients when processing zero-variance reward groups.
