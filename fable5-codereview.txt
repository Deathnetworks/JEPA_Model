Code Review Report: JEPA_Model Repository

Scope: model_architecture.py, train_latent_loop.py, train_decoder.py, train_rl_loop.py, GRPOLearningEngine.py, inference_harness.py, quantize_model.py
Severity legend: 🔴 S0 = crashes immediately · 🟠 S1 = runs but silently corrupts training · 🟡 S2 = design/performance flaw · ⚪ S3 = minor

ISSUE 1 — 🔴 Mamba2SSDBlock state-tensor shape mismatch (guaranteed crash)

Where: model_architecture.py, Mamba2SSDBlock.forward and Mamba2LatentLoop8B.forward (state init)

Why it's an issue. The recurrent state is initialized as:

mamba_state = torch.zeros(batch, self.nheads, self.d_state, self.d_state)  # (B, 128, 256, 256)

but the update writes an outer product of shape (d_state, d_head):

B_t   = B[:, t].unsqueeze(-1)          # (B, 128, 256, 1)
act_t = activated[:, t].unsqueeze(-2)  # (B, 128, 1, 64)
mamba_state = decay * mamba_state + dt_t * torch.matmul(B_t, act_t)  # (B,128,256,256) + (B,128,256,64)

(256, 256) cannot broadcast with (256, 64). Additionally, even if it could, the readout C_t @ state would produce d_state=256 per head, and out_tensor.view(batch, seq_len, self.d_inner) expects d_head=64 per head (128 × 64 = 8192), so the reshape would also fail (128 × 256 = 32768 ≠ 8192). The correct SSD state is (B, nheads, d_state, d_head): update H ← a·H + B⊗x, readout y = Cᵀ·H.

What happens if not changed. Every script that touches the engine — all three training loops, inference, GRPO — throws a RuntimeError on the very first forward pass. Nothing in this repo can run.

Alternative options. (a) Fix the shape and keep the hand-rolled recurrence; (b) replace the block with a vetted implementation; (c) transpose the state convention to (d_head, d_state) (equally valid, just be consistent).

Solution A — minimal shape fix:

# In BOTH Mamba2SSDBlock.forward and Mamba2LatentLoop8B fallback init:
if mamba_state is None:
    mamba_state = torch.zeros(batch, self.nheads, self.d_state, self.d_head,
                              device=x.device, dtype=x.dtype)

# update (unchanged math, now shape-consistent):
# state: (B,H,N,P);  B_t:(B,H,N,1);  act_t:(B,H,1,P)
mamba_state = decay * mamba_state + dt_t * (B_t @ act_t)     # (B,H,N,P)
out_t = (C_t @ mamba_state).squeeze(-2)                       # (B,H,1,N)@(B,H,N,P) -> (B,H,P) ✓

Explanation: the state per head becomes a d_state × d_head matrix, the outer product B⊗x matches it, and the contraction against C yields d_head per head, so the final .view(batch, seq, d_inner) is valid. One-line change in two places.

Solution B — replace with a validated pure-PyTorch SSD kernel:

# Adopt the reference "chunked SSD" from the Mamba2 paper (minimal PyTorch version):
def ssd_forward(x, dt, A, B, C, initial_state, chunk=64):
    # x:(B,L,H,P)  dt:(B,L,H)  B,C:(B,L,N)
    # 1. split L into chunks of 64
    # 2. intra-chunk: quadratic attention-like matmul (parallel)
    # 3. inter-chunk: cumulative decay recurrence over chunk states only (L/64 steps)
    # returns y:(B,L,H,P), final_state:(B,H,N,P)

Explanation: this is the standard "state space duality" formulation — mathematically identical, but the per-token Python loop is replaced by batched matmuls within chunks plus a short recurrence across chunk boundaries. It fixes the shape bug and Issue 2 at once, and there are reference implementations (mamba2-minimal, mamba_ssm's ssd_minimal_discrete) you can port and unit-test against.

Recommended: Solution B. Solution A makes the code correct but leaves it catastrophically slow (see Issue 2). Since you must touch this code anyway, port a reference chunked-SSD implementation with a unit test comparing it to the naive loop on tiny shapes. Fixing correctness and performance in one change is strictly better.

ISSUE 2 — 🔴/🟡 Per-token Python recurrence makes training computationally impossible

Where: Mamba2SSDBlock.forward — for t in range(seq_len):

Why it's an issue. The scan is a Python-level loop over up to 4,096 timesteps, executing 4 small matmuls each, per block, per forward. With 32 blocks that's ~131k sequential kernel launches per chunk per mini-batch — on XPU each launch has fixed overhead, so the GPU sits idle. Worse: under autograd, every timestep's intermediate state (B, 128, 256, 64) (≈4 MB bf16) is retained for backward → 4,096 × 32 blocks ≈ hundreds of GB of activation memory for a single sequence. torch.compile cannot rescue this — the data-dependent while loop above it plus the token loop cause pervasive graph breaks and recompilations.

What happens if not changed. If Issue 1 is fixed first, training will OOM immediately on any realistic sequence; on toy sizes it will run at seconds-per-token, making even one epoch take months.

Alternative options. (a) Chunked SSD (Issue 1, Solution B); (b) drastically shorten chunk length and gradient-checkpoint every block; (c) use the official mamba-ssm kernels (not viable on XPU — CUDA-only); (d) swap the mixer for something with native parallel form (e.g., gated linear attention / RetNet-style, which have O(L) chunk-parallel PyTorch implementations).

Solution A — chunked SSD (same as Issue 1B): parallel intra-chunk matmuls + inter-chunk recurrence. Memory for backward drops from O(L) states to O(L/chunk) states; compute becomes large dense matmuls that actually utilize the GPU.

Solution B — checkpointed short-chunk fallback (stopgap):

# keep the naive loop but:
chunk_size = 256                       # instead of 4096
for blk in self.blocks:
    out, state = torch.utils.checkpoint.checkpoint(blk, hidden, state, use_reentrant=False)
# and detach state across chunks (already done in the train loop)

Explanation: gradient checkpointing discards intra-block activations and recomputes them in backward, capping memory at one block's worth; 256-token chunks bound the Python-loop length. This makes small-scale experiments possible (still slow) without rewriting the kernel.

Recommended: Solution A. Solution B is only acceptable as a debugging stopgap while validating the loss/data pipeline at d_model=256. Any real training run needs the chunk-parallel scan; it's ~100 lines and well-documented in the Mamba2 literature.

ISSUE 3 — 🔴 vocab_size=151643 is too small for Qwen2.5's special tokens

Where: MambaJEPAEngine, ClosedLoopLatentDecoder, DualStageLatentDecoder (vocab_size=151643); inference_harness.py, GRPOLearningEngine.py

Why it's an issue. Qwen2.5's tokenizer assigns = 151643, = 151644, = 151645, etc. The inference harness sets pad_token_id = eos_token_id (an ID ≥ 151643), then seeds generation with:

gen_ids = torch.full((1, 1), self.tokenizer.pad_token_id, ...)  # id 151643+
self.token_embedding(gen_ids)  # Embedding(151643, ...) → index out of range!

nn.Embedding(151643, d) accepts indices 0–151642 only. Any special token — pad seed, EOS in training data, chat-template markers in the frontier traces — is out of bounds.

What happens if not changed. IndexError: index out of range in self on the first decode step of inference and every GRPO rollout; intermittent crashes during training whenever a shard contains a special token (chat traces almost certainly do). The EOS-based stopping criterion is also unlearnable since EOS can't even be represented.

Alternative options. (a) Enlarge the embedding tables; (b) remap/strip special tokens in the data pipeline and use a custom stop token; (c) switch to a tokenizer whose specials fit (fragile).

Solution A — size vocab from the tokenizer (correct fix):

tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
vocab = max(len(tokenizer), tokenizer.vocab_size)   # ≈ 151665; round up:
vocab = ((vocab + 63) // 64) * 64                    # pad to multiple of 64 for GEMM efficiency
model  = MambaJEPAEngine(vocab_size=vocab, ...)
decoder = ClosedLoopLatentDecoder(vocab_size=vocab, ...)

Explanation: derive the embedding size from the actual tokenizer at construction time instead of a hardcoded constant; padding to a multiple of 64 improves matmul throughput. Every ID the tokenizer can emit is now representable, including pad/EOS.

Solution B — sanitize IDs at the data boundary:

def sanitize(ids, vocab_size, unk_id):
    return torch.where(ids >= vocab_size, torch.tensor(unk_id), ids)
# apply in Dataset.__getitem__, in tokenizer wrapper for inference, and use a
# dedicated in-vocab token (e.g., last ordinary id) as pad/eos everywhere.

Explanation: clamp out-of-range IDs to a designated in-vocab token and standardize pad/EOS to in-range IDs. No architecture change, but you lose the semantics of chat-structure tokens and must keep the sanitizer in sync across 4 scripts.

Recommended: Solution A. It's a two-line fix at construction, removes an entire class of crashes, and preserves special-token semantics that the chat-formatted training data depends on. Solution B is a leaky patch that must be replicated everywhere tokens enter the system.

ISSUE 4 — 🔴 train_decoder.py latent-dimension mismatch (1024 data vs 5120 model)

Where: train_decoder.py XPU path: model = ClosedLoopLatentDecoder() (default d_latent=5120) vs shard target_concept = BGE-M3 vectors (1024-d)

Why it's an issue. The decoder's first layer is nn.Linear(5120, 16*6144). The dataset feeds it 1024-d BGE vectors:

logits = model(decoder_input, target_concept)   # concept_to_memory(1024-d input into 5120-d Linear)

What happens if not changed. RuntimeError: mat1 and mat2 shapes cannot be multiplied (N×1024 and 5120×98304) on the first mini-batch of every XPU run. (The CPU debug path "works" only because it happens to pass d_latent=1024.) There's also a conceptual mismatch: this script pretrains the decoder on raw BGE space, but train_latent_loop.py feeds it the engine's 5120-d hierarchical concept, so even a shape-fixed version pretrains against a different input distribution.

Alternative options. (a) Pretrain on padded/projected BGE vectors; (b) pretrain only the micro slice and zero the macro slice; (c) skip decoder pretraining entirely and train jointly (the tripartite loss already trains the decoder).

Solution A — micro-slice conditioning consistent with the hierarchy:

model = ClosedLoopLatentDecoder(d_latent=5120)
...
bge = torch.stack(target_concepts_list)                 # (B, 1024)
concept = torch.zeros(bge.size(0), 5120)
concept[:, :1024] = bge                                  # micro slot = BGE; macro slot = 0
logits = model(decoder_input, concept.to(device))

Explanation: the main training loop aligns student_concept[:, :1024] to BGE and encourages the macro slice toward 0 via the energy-contraction penalty — so "BGE in the micro slot, zeros in macro" is exactly the distribution the decoder will later see early in joint training. Pretraining becomes consistent instead of contradictory.

Solution B — drop the pretraining stage:

# Delete train_decoder.py from the pipeline; rely on train_latent_loop.py,
# optionally freezing the engine for the first N steps so the decoder
# warm-starts against near-static concepts:
if step < decoder_warmup_steps:
    for p in engine.parameters(): p.requires_grad_(False)

Explanation: since the decoder is trained end-to-end by the CE term anyway, a separate stage on a mismatched input distribution adds risk without clear benefit; freezing the engine briefly reproduces the "stable conditioning" benefit inside one script.

Recommended: Solution A if you want the staged curriculum (cheap and now distributionally consistent); otherwise B for simplicity. Either way, add an assertion assert concept.size(-1) == model.concept_to_memory.in_features so this class of mismatch fails loudly with a clear message.

ISSUE 5 — 🔴 DeepSpeed configuration cannot initialize (multi-model prepare, Windows, XPU, client optimizer + CPU offload)

Where: train_latent_loop.py, train_rl_loop.py

Why it's an issue. Four independent blockers stack:
1. Two models, one Accelerator + DeepSpeed: accelerator.prepare(model, decoder, optimizer, ...) raises ValueError: You can't use same Accelerator() instance with multiple models when using DeepSpeed.
2. Windows: paths (F:\JEPA_Model...) indicate Windows; DeepSpeed training — especially the DeepSpeedCPUAdam C++ op required by optimizer offload — does not build/run there.
3. Client optimizer + ZeRO offload: you pass a vanilla torch.optim.AdamW; DeepSpeed's optimizer offload requires its own CPU Adam (ZeRO-Offload can only work with DeepSpeed optimizers), and Accelerate forces that check by default.
4. XPU: stock DeepSpeed's accelerator abstraction for XPU is spotty; on one GPU, ZeRO-2's partitioning provides zero benefit anyway (there is nothing to shard across).

What happens if not changed. Both training scripts terminate during setup — before any of the other bugs even get the chance to fire. If you ever "fix" enough to initialize, ZeRO-2 still keeps full gradients + fp32 master weights for a ~9B-param model, which cannot fit regardless (see Issue 12).

Alternative options. (a) Remove DeepSpeed and manage memory manually; (b) wrap engine+decoder into one nn.Module and move to Linux/WSL2 with an XPU-enabled DeepSpeed build; (c) use FSDP (also awkward on single-GPU XPU); (d) use a paged/8-bit or CPU-offloaded optimizer without any distributed framework.

Solution A — drop DeepSpeed; plain single-device loop with explicit accumulation:

class FullModel(nn.Module):                      # single module = single state_dict, single prepare target
    def __init__(self):
        self.engine = MambaJEPAEngine(...)
        self.decoder = ClosedLoopLatentDecoder(...)

model = FullModel().to("xpu")
opt = torch.optim.AdamW(model.parameters(), lr=3e-4, betas=(0.9,0.95), weight_decay=0.1)

for step, batch in enumerate(loader):
    with torch.autocast("xpu", torch.bfloat16):
        loss = compute_loss(model, batch) / ACCUM
    loss.backward()
    if (step + 1) % ACCUM == 0:
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        opt.step(); sched.step(); opt.zero_grad(set_to_none=True)

Explanation: on a single GPU, Accelerate+DeepSpeed adds failure modes and removes control while providing nothing you can't do in ten lines. You own the accumulation boundary, clipping, scheduler, and checkpoints — which also eliminates Issues 6 and 7 below.

Solution B — keep Accelerate/DeepSpeed properly (Linux/WSL2 only):

model = FullModel()                               # ONE module (fixes multi-model crash)
# no client optimizer; let DeepSpeed create its own:
ds_plugin = DeepSpeedPlugin(zero_stage=2, offload_optimizer_device="cpu",
                            gradient_accumulation_steps=16, gradient_clipping=1.0)
# in the ds config: optimizer: {type: "AdamW", params: {...}}  → DeepSpeedCPUAdam used internally
model, dataloader, sched = accelerator.prepare(model, dataloader, sched)
# training loop: ONLY accelerator.backward(loss); NO manual loss scaling; NO manual optimizer.step()
with accelerator.accumulate(model):
    loss = ...
    accelerator.backward(loss)

Explanation: fixes each blocker — single wrapped module, DeepSpeed-native offload optimizer, Linux runtime, and delegating accumulation entirely to the engine so there's exactly one stepping mechanism.

Recommended: Solution A. Single GPU + XPU + (currently) Windows is precisely the environment DeepSpeed handles worst, and ZeRO's core value (sharding across ranks) is nil here. A manual loop is simpler, debuggable, and portable. Revisit DeepSpeed/FSDP only if you add GPUs.

ISSUE 6 — 🟠 Checkpoint round-trip silently loads nothing (torch.compile prefixes + strict=False)

Where: all scripts that save/load jepa_engine.pth / latent_decoder.pth

Why it's an issue. Models are compiled (torch.compile) before load_state_dict(..., strict=False) and before saving. Compiled modules prefix every key with _orig_mod. (and Accelerate/DeepSpeed wrapping adds module.). So:
- Saving writes mangled keys (_orig_mod.embedding.weight, ...).
- Loading a plain checkpoint into a compiled model matches zero keys, and strict=False suppresses the error.
- quantize_model.py loads with strict=True and will hard-crash on the mangled keys instead.

What happens if not changed. Every stage of the pipeline logs "Successfully loaded ..." while actually running on random weights. The staged curriculum (decoder pretrain → latent loop → RL → inference) silently never composes; RL "fine-tunes" a random network; inference generates noise; you would burn weeks before noticing. This is the most dangerous failure mode in the repo because nothing crashes.

Alternative options. (a) Save/load only unwrapped state dicts; (b) load before compiling; (c) strip prefixes on load; (d) never use strict=False for "should exist" checkpoints.

Solution A — canonical save/load discipline:

# SAVE (always unwrap):
raw = accelerator.unwrap_model(model) if using_accelerate else getattr(model, "_orig_mod", model)
torch.save(raw.state_dict(), path)

# LOAD (before compile/wrap, strict, loud):
model = FullModel()
missing, unexpected = model.load_state_dict(torch.load(path, weights_only=True), strict=True)
model = torch.compile(model)     # compile AFTER loading

Explanation: state dicts always live in "plain module" key-space; compilation/wrapping happens strictly afterward; strict=True turns any drift into an immediate, explicit error instead of silent randomness.

Solution B — defensive prefix-stripping loader (for existing mangled checkpoints):

def clean_load(model, path):
    sd = torch.load(path, weights_only=True)
    sd = { k.removeprefix("module.").removeprefix("_orig_mod."): v for k, v in sd.items() }
    missing, unexpected = model.load_state_dict(sd, strict=False)
    loaded = len(sd) - len(unexpected)
    assert loaded / max(len(model.state_dict()),1) > 0.99, \
        f"Only {loaded} keys loaded; missing={missing[:5]} unexpected={unexpected[:5]}"

Explanation: normalizes any historical checkpoint and — critically — converts "silent zero-key load" into an assertion failure with diagnostics, while still tolerating genuinely-new heads.

Recommended: Both, in roles: Solution A as the permanent policy (it prevents the problem), Solution B as a one-time migration utility for checkpoints already on disk. The load-coverage assertion should stay forever; strict=False without a coverage check should be banned from the codebase.

ISSUE 7 — 🟠 Gradient accumulation is triple-implemented and mutually conflicting

Where: train_latent_loop.py

Why it's an issue. Three mechanisms fight over the same job:
1. Accelerator/DeepSpeedPlugin(gradient_accumulation_steps=16) — DeepSpeed scales losses by 1/16 internally and steps on its own count of backward() calls;
2. manual scaling loss / (accumulation_steps * num_chunks) — dividing by 16 a second time (effective LR silently ~16× lower);
3. manual optimizer.step() every 16 mini-batches — a no-op under DeepSpeed (the wrapped optimizer defers to the engine), while DeepSpeed's real step boundary lands wherever its backward-call counter says, which is decoupled from mini-batch boundaries because each mini-batch fires a variable number of backwards (one per 4096-token chunk).

What happens if not changed. Even if the setup crashes of Issue 5 were resolved: double-scaled gradients, optimizer steps at arbitrary points mid-mini-batch, an LR scheduler stepping out of sync with actual updates, and gradient clipping applied to partial accumulations. Training would converge slowly, erratically, or not at all — with no error message ever.

Alternative options. (a) One manual mechanism (with Issue 5A); (b) delegate fully to the framework (with Issue 5B); (c) treat each chunk backward as the accumulation unit rather than each mini-batch, since chunk count varies.

Solution A — single manual mechanism, chunk-aware:

ACCUM_TOKENS = 65536                       # accumulate by tokens, not by mini-batches
tokens_seen = 0
for chunk in chunks(batch):
    loss = compute_loss(chunk) * (chunk.numel() / ACCUM_TOKENS)  # exact weighting, single scale
    loss.backward()
    tokens_seen += chunk.numel()
    if tokens_seen >= ACCUM_TOKENS:
        clip_(); opt.step(); sched.step(); opt.zero_grad(); tokens_seen = 0

Explanation: because sequences have variable chunk counts, "divide by 16" mini-batch accounting is wrong anyway; token-weighted scaling makes every optimizer step correspond to a fixed effective batch in tokens, giving one unambiguous scale factor and step boundary.

Solution B — full framework delegation:

with accelerator.accumulate(model):
    loss = compute_loss(...)               # NO manual division
    accelerator.backward(loss)             # framework scales AND steps at the right boundary
# remove all manual optimizer.step()/zero_grad(); step scheduler via accelerator sync flag:
if accelerator.sync_gradients:
    sched.step()

Explanation: exactly one owner of accumulation. Works only after Issue 5B's restructuring (single module, DS-native optimizer), and note accumulate() counts forward/backward calls, so you must restructure so one call = one chunk with consistent semantics.

Recommended: Solution A, paired with Issue 5's Solution A. Variable chunks-per-sample make framework accumulation counters semantically wrong here; explicit token-based accounting is the only version that is actually correct, not just non-crashing.

ISSUE 8 — 🟠 GRPO reward is trivially hackable: empty output compiles

Where: GRPOLearningEngine.compute_verifiable_reward

Why it's an issue. rustc --crate-type=lib on an empty file (or a file containing only comments, or pub fn f(){}) exits 0. The reward is r_compile − γ·avg_loops with γ=0.01. The globally optimal policy is therefore: emit nothing (or a trivial item) and route with minimal loops → reward ≈ 1.0 every time, with far less variance than actually writing correct code. There is no term for relevance to the prompt, code length, tests passing, or even non-emptiness. Secondary problems: fixed temp filename grpo_eval_scratch.rs collides across concurrent processes; 5s timeout is tight for cold rustc on Windows; a random untrusted string is compiled on the host (rustc is mostly safe at compile-time, but include!/path tricks and proc-macro-adjacent surface deserve at least a sandbox/cwd jail).

What happens if not changed. Classic reward hacking: within a few hundred GRPO steps the policy collapses to emitting empty/trivial compiling snippets. Group-relative advantages then go to ~0 (all rewards identical), σ gets clamped to 1e-6, and learning stalls permanently at the degenerate solution. Before collapse, early training has the opposite problem — a random-weight decoder never compiles anything, so all rewards equal −γ·loops, advantages ≈ router noise, and text-policy gradients are meaningless.

Alternative options. (a) Richer verifier (compile and run unit tests); (b) shaped reward (compile + non-triviality + prompt-relevance terms); (c) curriculum: only enable RL after SFT reaches some compile-rate threshold; (d) reject-sampling/filtering instead of policy gradients.

Solution A — test-based verifiable reward:

def reward(prompt_meta, code):
    src = code + "\n" + prompt_meta["test_harness"]     # e.g. #[cfg(test)] mod tests {...}
    write(tmp_unique_file, src)                          # tempfile.mkstemp → no collisions
    build = run(["rustc", "--test", tmp, "-o", exe], timeout=30)
    if build.returncode != 0: return 0.0
    tests = run([exe], timeout=10)                       # in a jailed temp cwd
    if tests.returncode != 0: return 0.3                 # compiles but fails tests
    return 1.0

Explanation: pair each RL prompt with a small test harness (Magicoder-style instructions can be augmented, or start from datasets that ship tests). "Compiles" alone is nearly information-free for Rust libs; "passes tests" is a real verifiable signal and is not satisfied by empty output because the harness references the required items — empty code then fails to compile against the tests, closing the hack.

Solution B — shaped anti-degenerate reward (no test data needed):

def reward(prompt, code, global_steps):
    if len(code.strip()) < MIN_CHARS:              return -0.5      # emptiness penalty
    r_compile = 1.0 if compiles(code) else 0.0
    r_struct  = 0.2 * min(1.0, count_items(code)/2)                 # fn/struct/impl present
    r_rel     = 0.3 * cosine(bge(prompt), bge(code))                # reuses existing BGE model
    return r_compile + r_struct + r_rel - 0.01*avg_loops

Explanation: explicitly prices out the degenerate optimum (emptiness penalized, structure and prompt-relevance rewarded). Weaker than real tests — cosine relevance is gameable in principle — but implementable today with components already in the repo (BGE-M3 embedder).

Recommended: Solution A, with Solution B's emptiness/min-length guard kept as a cheap belt-and-braces term. Verifiable-reward RL lives or dies on the verifier actually verifying the task; compile-only Rust rewards demonstrably don't. Also switch to tempfile and run the compiler in an isolated working directory regardless of which option you choose.

ISSUE 9 — 🟠 GRPO re-evaluation log-probs are off by one → PPO ratios are garbage

Where: GRPOLearningEngine.train_grpo_step, step 3

Why it's an issue. During rollout, the log-prob stored for token tᵢ is computed from the decoder fed prefix [pad, t₀ … tᵢ₋₁] (logits at the last position predict tᵢ). During re-evaluation with gradients:

logits = self.decoder(group_tokens[idx], student_concept)     # input: [t0 … t_{n-1}] — no pad seed!
target_log_probs = log_probs.gather(-1, group_tokens[idx].unsqueeze(-1))  # gathers t_i at position i

Position i of these logits is the prediction after seeing t₀…tᵢ — i.e., the model's probability of tᵢ₊₁. Gathering tᵢ there computes "probability of repeating the current token", not the rollout action's probability. So ratio = exp(new − old) compares two different random variables. Additionally, the whole thing runs inside the caller's autocast and PPO clipping then operates on noise.

What happens if not changed. The policy-gradient signal is not merely noisy — it is systematically wrong (it reinforces token repetition patterns weighted by advantage). Combined with Issue 8's degenerate rewards, RL will actively damage whatever the SFT stage produced. No error is raised.

Alternative options. (a) Fix the shift (input gen_ids[:, :-1], gather gen_ids[:, 1:]); (b) skip re-evaluation entirely and use the REINFORCE/GRPO form on rollout log-probs (requires gradient-enabled sampling); (c) mask post-EOS positions in the sum (currently every position counts).

Solution A — correct teacher-forced re-scoring:

full = torch.cat([pad_seed, group_tokens[idx]], dim=1)   # [pad, t0 … t_{n-1}]
logits = decoder(full[:, :-1], student_concept)           # positions predict t0 … t_{n-1}
logp   = F.log_softmax(logits.float(), dim=-1)            # fp32 for numerical stability
new_lp = logp.gather(-1, group_tokens[idx].unsqueeze(-1)).squeeze(-1)   # aligned with rollout lp
mask   = valid_token_mask(group_tokens[idx], eos_id)      # zero-out post-EOS
ratio  = torch.exp((new_lp - old_lp) * mask)

Explanation: reconstructs exactly the conditioning used at sampling time, so new_lp and old_lp are the same quantity under new vs. old parameters — which is what the PPO ratio requires by definition. The fp32 softmax and EOS mask remove two secondary corruption sources.

Solution B — single-pass GRPO without re-evaluation:

# sample WITH grad on the decoder pass (no torch.no_grad around decoding):
for step in range(max_gen):
    logits = decoder(gen_ids, concept.detach())
    tok = sample(logits[:, -1])
    lp_list.append(log_softmax(logits[:,-1]).gather(-1, tok))
loss = -(advantage.detach() * torch.stack(lp_list).sum())  # REINFORCE w/ group-relative baseline

Explanation: with exactly one gradient step per group, PPO's ratio is 1 anyway; the clipped-surrogate machinery buys nothing. Sampling with grad and applying the group-normalized advantage directly is the vanilla GRPO objective, eliminates the off-by-one risk structurally, and halves the forward passes. Cost: the sampling graph is kept in memory (bounded by max_gen=256 decoder-only passes; the engine stays under no_grad).

Recommended: Solution A if you plan multiple inner epochs per group later (then clipping matters); Solution B for the current single-update design — it's simpler, cheaper, and immune to alignment bugs. Given this codebase's track record with index alignment, I'd pick B.

ISSUE 10 — 🔴 Test-time GRPO weight updates in the inference harness ("AdaJEPA") are infeasible and destructive

Where: inference_harness.py (self.optimizer = AdamW(engine+decoder params); on compile failure → train_grpo_step → loss.backward() → optimizer.step())

Why it's an issue.
- Memory: AdamW keeps two fp32 states per parameter. For this ~9B-param stack that's ~72 GB the moment optimizer.step() first runs — on an inference box.
- Graph retention: train_grpo_step(group_size=2) returns the sum of two full policy graphs (engine forward + 256 decoder forwards each); backward through them will OOM long before the optimizer does.

        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        optimizer.step()
        lr_scheduler.step()
        optimizer.zero_grad()
